# ADR-031: Requirement Generation and Merge Contract

- **Status:** Accepted
- **Date:** 2026-09-07
- **Story:** S1-I02 — Requirement Generation
- **Extends:** ADR-030 Requirement Domain and Provenance Contract

## Context

The approved Backlog and AI Workflow require Requirement generation from a specific Context
Version, unsupported classification, duplicate handling, conflict visibility and metered AI calls.
The owner resolved the previously open snapshot, merge, replay, repair and atomicity details on
2026-09-06. I02 must remain provider-neutral and must not introduce the later Gap, API or UI model.

## Decision

- Input is an exact, sorted revision vector of `(context_item_id, updated_at)` for the requested
  Context Version and statuses `proposed|confirmed`. The complete set is compared again inside the
  final persistence transaction. Insert, update or predicate exit causes
  `CONTEXT_SNAPSHOT_CHANGED`, no Requirement/Outbox write and no hidden refresh by the same Job.
- Candidate output is exactly title, description, category, priority, Source References,
  confidence, unsupported, duplicate group key and conflict group key. Application owns
  `status=draft` and `created_by_type=ai`.
- `is_unsupported=false` requires at least one valid reference from the immutable input Snapshot.
  Unsupported candidates may have an empty reference list. Source Reference semantics are not
  extended with supporting/contradicting meanings.
- Within a duplicate group, merge is allowed only when title, description, category, priority and
  unsupported are exactly equal. Confidence is ignored for equality and the first candidate value
  is retained. Source References use stable union. Any semantic disagreement is the repairable
  `DUPLICATE_CLASSIFICATION_CONFLICT`.
- Existing active Requirements keep title, description, priority, confidence, status and creator;
  AI may only stable-union new Source References. A removed match without genuinely new evidence
  is ignored. New evidence creates a new draft and never reactivates the removed row.
- Conflicting candidates persist as independent Requirements. A safe
  `requirement.conflict_detected` Outbox event with Project, Context Version and Requirement IDs is
  inserted in the same transaction. I02 adds no conflict table and no Gap.
- `generation_job_id` is nullable and non-unique because one Job creates a batch. The tenant-first
  `(account_id, project_id, generation_job_id)` index supports replay. Replay first resolves the
  same-tenant Job: `succeeded` loads the current Requirement rows generated by that Job, while
  `failed` replays its safe terminal error. Neither path calls AI, appends Usage or creates a write.
  An empty validated candidate batch fails with `INSUFFICIENT_CONTEXT`. A succeeded Job with no
  generated rows is an empty terminal replay; no historical immutable payload is promised.
- I02 does not create `requirement_generation_results`, a generation-batch table or a Job
  `result_ref`. Historical pre-edit payload replay is a separate future contract. Jobs remain the
  execution-state source of truth and `requirements.generation_job_id` remains the successful
  generated-row association.
- Requirement/provenance changes and required Outbox events commit together or all roll back.
  Usage records remain independent and one record is appended for every AI or repair invocation.
- Repair policy is explicit and versioned with `max_repairs` exactly zero or one and no default.
  Only schema, model provenance, duplicate classification and support classification defects are
  repairable. Provider, persistence, snapshot, insufficient-context and tenant failures are not.
  Repair uses the same AIExecutionPort, Workflow and routing decision without hidden escalation.
- Contract/CI uses a deterministic fake provider. Real provider selection remains deferred to
  G02/G03. No provider SDK, endpoint, model or credential name enters Application or Domain.
- Operational logs use the approved event names and identifier/version/count/duration/reason
  fields only. Context content, Requirement text, Source References, model output, prompt,
  validation free text and credentials are prohibited.

## Consequences

The final PostgreSQL transaction uses a short Project row lock and `SHARE` lock on Context Items to
make the exact-set comparison include phantom inserts as well as updates and state exits. This is a
broad lock and is intentionally confined to the short persistence phase after AI execution; its
contention must be measured before scaling. The transactional Outbox preserves downstream conflict
visibility without prematurely creating the J01 Gap domain.

## Deferred

- Concrete Provider adapters and model-quality evaluation (G02/G03 and I05).
- Queue message, scheduler, retry and ACK wiring.
- Requirement HTTP lifecycle, `acceptance_note` and UI (I03/I04).
- Conflict-to-Gap transformation (J01/J02).
- Fuzzy/linguistic deduplication, confidence aggregation and removed-item restoration.
- Immutable historical generation payload/batch audit or replay after I03 mutations.
