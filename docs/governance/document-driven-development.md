# سیاست توسعهٔ کاملاً مستندمحور

## اصل پایه

هیچ قابلیت، رفتار، فیلد، مقدار پیش‌فرض، integration، انتخاب فنی یا تغییر ساختاری صرفاً بر اساس حدس توسعه‌دهنده پیاده نمی‌شود. توسعه فقط از requirement صریح و قابل ارجاع آغاز می‌شود.

## ترتیب اعتبار منابع

1. درخواست صریح و فعلی کاربر.
2. `AGENTS.md` و اصلاحات صریح بعدی کاربر.
3. آخرین اسناد Approved/FINAL پروژه‌ی `Aria AI` در Google Drive؛ لینک دقیق سند باید در رکورد Increment ثبت شود.
4. mirror همگام‌شده‌ی اسناد محصول در `docs/product/`.
5. معماری و ADRهای accepted در Google Drive، سپس mirror محلی در `docs/architecture/` و `docs/adr/`.
6. قراردادهای machine-readable در `packages/contracts/`.
7. `design-system/MASTER.md` برای رفتار و ساختار UI.
8. مستندات توسعهٔ incrementهای قبلی، فقط برای history و نه ایجاد requirement جدید.

راهنماها، نمونه‌ها و Customer Discovery شبیه‌سازی‌شده نمی‌توانند به‌تنهایی requirement جدید بسازند.

## فرآیند پیش از توسعه

1. اسناد مرتبط کامل خوانده می‌شوند.
2. requirementها با شناسهٔ `REQ-NNN` در `development.md` استخراج می‌شوند.
3. برای هر requirement، منبع، محل implementation و test case مشخص می‌شود.
4. ساختارهای تحت تأثیر فهرست و روش حفظ آن‌ها ثبت می‌شود.
5. اگر اطلاعات لازم وجود ندارد، توسعهٔ همان بخش متوقف و سؤال مشخص از کاربر پرسیده می‌شود.

## موارد الزام‌آور برای سؤال از کاربر

- دو سند معتبر با یکدیگر تعارض دارند.
- رفتار success/error/empty یا سطح دسترسی مشخص نیست.
- schema، مقدار پیش‌فرض، limit، retention، قیمت یا workflow مستند نشده است.
- انتخاب provider، framework، سرویس خارجی یا dependency جدید لازم است ولی تصویب نشده است.
- انجام درخواست نیازمند تغییر مرز ماژول، قرارداد عمومی، ساختار پوشه یا design system است.
- چند تفسیر ممکن اثر متفاوتی بر محصول، داده، امنیت یا تجربهٔ کاربر دارند.

سؤال باید دقیقاً شکاف موجود و اثر گزینه‌ها را بیان کند. تا دریافت پاسخ، بخش‌های مستقل و بدون ابهام می‌توانند ادامه پیدا کنند؛ بخش مبهم پیاده نمی‌شود.

## حفظ ساختار

- معماری modular monolith و boundaryهای مستند حفظ می‌شوند.
- نام‌گذاری، schema versioning، token hierarchy و قراردادهای موجود بدون مجوز شکسته نمی‌شوند.
- فایل یا section موجود صرفاً برای ساده‌تر شدن implementation حذف، جابه‌جا یا بازطراحی نمی‌شود.
- هر structural change باید در بخش `Structure Preservation` رکورد توسعه توضیح و به تأیید کاربر یا ADR مربوط متصل شود.

## Traceability اجباری

هر رکورد تکمیل‌شده حداقل جدول زیر را دارد:

| Requirement | Source | Implementation | Tests |
|---|---|---|---|
| REQ-001 | مسیر سند یا نقل درخواست کاربر | مسیر فایل/بخش | TC-001 |

هیچ ردیفی نباید Source، Implementation یا Tests خالی داشته باشد. requirement خارج از این جدول بخشی از تحویل تأییدشده نیست.

## کنترل فرضیات

در هر `development.md` عبارت زیر الزامی است:

```text
**Unapproved assumptions:** None
```

اگر توسعه به تصمیمی نیاز دارد که منبع مستند ندارد، این عبارت نباید با حدس حفظ شود؛ باید سؤال پرسیده، پاسخ کاربر به‌عنوان clarification ثبت و سپس requirement به‌روزرسانی شود.

## پایان توسعه

increment فقط زمانی کامل است که:

- تمام requirementهای traceability پیاده و تست شده باشند.
- ساختار مستند حفظ شده یا تغییر مصوب آن ثبت شده باشد.
- هیچ فرض تأییدنشده‌ای باقی نمانده باشد.
- senior review و گزارش تست نهایی PASS باشند.
- `npm test` و `npm run validate` پاس شوند.
